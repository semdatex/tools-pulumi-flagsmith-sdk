# `@semdatex/pulumi-flagsmith` — generated Pulumi SDK for the Flagsmith Terraform provider

> [!IMPORTANT]
> **This is not an official Pulumi package.** Pulumi does not publish an SDK for
> the Flagsmith provider. This repository is SEMDATEX's committed output of
> **Pulumi's own dynamic-bridge codegen** (`pulumi package gen-sdk
> terraform-provider Flagsmith/flagsmith`), checked in so it can be consumed as a
> pinned dependency. It is not published to npmjs.com, it is not supported by
> Pulumi, and it is not supported by Flagsmith.
>
> Codegen names the package `@pulumi/flagsmith`; `scripts/repackage.sh` renames
> it to `@semdatex/pulumi-flagsmith` on every regeneration. The `@pulumi` scope
> belongs to Pulumi — we could never publish under it, and it reads as an
> official package at every import site. Owning the scope keeps publishing to npm
> a decision we can take later rather than a migration across every consumer.
> The name is not load-bearing: resource tokens are `flagsmith:index/...`, taken
> from the provider schema, and runtime plugin resolution reads the
> `pulumi.parameterization` block in `package.json`, never the package name.

> [!NOTE]
> **The SDK in this repository was generated by CI, not committed by hand.** It
> is the output of the **Regenerate SDK** workflow running `scripts/regenerate.sh`
> at the pins declared in [`pins.yml`](pins.yml), so its provenance is the
> pipeline itself.
>
> That first run reproduced the SDK previously validated end-to-end in
> more-platform **byte-for-byte** — all 19 generated files matched a recorded
> fingerprint of that artifact — using Pulumi CLI `v3.256.0`, which is now
> pinned in `pins.yml` so codegen output stops drifting with whatever Pulumi
> ships that week. (The fingerprint scaffolding was bootstrap-only and has been
> removed; regeneration now diffs against the committed SDK itself.)

## Why this repository exists

Pulumi can bridge any Terraform provider dynamically. For a **dynamic** bridge
there is no published SDK — Pulumi's prescribed model is to generate the SDK
locally and commit it into the repo that consumes it.

That worked, but it put ~2,100 lines of generated TypeScript, plus a codegen bug
workaround, inside an application repo, and made every provider bump a
hand-run workstation task. This repository moves that lifecycle somewhere it can
be owned properly: CI regenerates, patches, builds and version-tags the SDK, and
consumers depend on an immutable tag.

**It is public on purpose.** Consumption is an anonymous git URL — no registry,
no token, no auth in any consumer or CI job. A private repo would force every
consumer to carry a credential purely to resolve a dependency.

## Consuming it

Pin a tag. Never depend on a branch.

```bash
npm install github:semdatex/tools-pulumi-flagsmith-sdk#v0.10.0-sdk.1
```

or in `package.json`:

```json
{
  "dependencies": {
    "@semdatex/pulumi-flagsmith": "github:semdatex/tools-pulumi-flagsmith-sdk#v0.10.0-sdk.1"
  }
}
```

> [!WARNING]
> **Pin the exact tag. Do not use npm's `#semver:` range syntax.**
>
> ```
> #semver:^0.10.0     <-- matches NOTHING here
> ```
>
> npm parses git tags as semver when you use a range, and `0.10.0-sdk.1` is
> formally a *prerelease* of `0.10.0` — semver ranges exclude prereleases, so
> the range silently resolves to nothing rather than failing loudly.
>
> This is a deliberate trade-off, not an oversight: see
> [Versioning](#versioning) for why the tag carries a packaging revision.

```ts
import * as flagsmith from "@semdatex/pulumi-flagsmith";

const project = new flagsmith.Project("my-project", { /* ... */ });
const feature = new flagsmith.Feature("my-flag", { /* ... */ });
```

### Zero lifecycle scripts

The compiled output in `bin/` is **committed**, and this repo's copy of the
package has **no `postinstall`, `prepare`, or any other lifecycle script**. That
is deliberate and it is the main thing that makes it safe as a git dependency:

- it installs correctly under `npm ci --ignore-scripts` / `ignore-scripts=true`,
  which many hardened CI setups set globally;
- it sidesteps npm's confusing prepare-vs-postinstall semantics for git
  dependencies, where the hook that builds the package may or may not run
  depending on npm version and install flags.

Pulumi's generated package builds itself in a `postinstall`. We remove that hook
and commit the build output instead. CI enforces that `bin/` matches the sources
on every PR, so the two cannot drift.

### The runtime plugin still gets fetched

Installing this package does **not** vendor the provider binary. At
preview/deploy time Pulumi resolves the bridged plugin using the
`pulumi.parameterization` block in `package.json`:

| Field | Value |
|---|---|
| Bridge plugin | `terraform-provider` **1.3.0** |
| Provider | `registry.opentofu.org/flagsmith/flagsmith` **0.10.0** |

So any environment that runs `pulumi preview`/`up` against this SDK needs egress
to Pulumi's plugin releases and to `registry.opentofu.org` — the same class of
egress as a Helm repo fetch. That block is load-bearing: CI asserts it is present
and matches the pins on every regeneration.

## Versioning

| | |
|---|---|
| `package.json` `version` | the **provider** version — `0.10.0` |
| Git tag | `v<provider>-sdk.<n>` — e.g. `v0.10.0-sdk.1` |

`<n>` increments for regenerations that change the output **without** a provider
bump: a bridge-plugin upgrade, a change to the patch, a packaging fix. A provider
bump resets it to `.1` (`v0.11.0-sdk.1`).

The npm version alone cannot express "same provider, different generated
output", which is exactly why the tag carries the extra segment — and the tag,
not the version, is what consumers pin.

The upstream provider version is the tag's **prefix, verbatim** — upstream tags
`v0.10.0`, and so do we, plus a packaging revision. So the provider a given SDK
release was built from is readable straight off the tag, and every build for one
provider version is one glob away:

```bash
git tag --list 'v0.10.0*'
# v0.10.0-sdk.1
# v0.10.0-sdk.2   <- bridge 1.3.0 -> 1.4.0, same provider
```

This is the same split Debian and RPM use (`0.10.0-1`): upstream version, then a
packaging revision that moves independently. It is needed because tags here are
**immutable** — a repository ruleset blocks updating and deleting any `v*-sdk.*`
tag. Without the revision, a bridge upgrade or a change to `patch-sdk.sh` that
altered the generated output while the provider stayed at `0.10.0` would have no
tag left to cut, and `v0.10.0` could not be moved. If a release is wrong, cut a
new one.

The cost of that choice is the semver-prerelease caveat in
[Consuming it](#consuming-it): `0.10.0-sdk.1` sorts *below* `0.10.0` and is
excluded from semver ranges. Pinning exact tags — which is the documented and
intended usage — is unaffected.

## The patch, and the upstream bug it works around

The generated SDK **does not compile unpatched**. Pulumi's nodejs codegen emits a
`<Name>State` interface for every resource. Flagsmith has both
`flagsmith_feature` and `flagsmith_feature_state`, so `index.ts` exports
`FeatureState` twice — once as `Feature`'s state interface, once as the
`FeatureState` resource class:

```
index.ts: error TS2323: Cannot redeclare exported variable 'FeatureState'.
index.ts: error TS2484: Export declaration conflicts with exported declaration of 'FeatureState'.
```

[`scripts/patch-sdk.sh`](scripts/patch-sdk.sh) fixes this with a single
type-level alias, renaming *the interface* on the `./feature` re-export line:

```ts
export { FeatureArgs, FeatureState as FeatureResourceState } from "./feature";
```

The resource class keeps its name and its provider mapping, so **no runtime
behaviour changes** — only a type this program never uses is renamed. The script
is idempotent, detects and no-ops if upstream ever fixes codegen, and fails
loudly with instructions if the generated shape drifts into something it does not
recognise.

A draft of the upstream bug report lives in
[`docs/upstream-issue.md`](docs/upstream-issue.md). It has **not** been filed yet
— filing needs a human decision. When it is filed and fixed, `patch-sdk.sh`
becomes a no-op and can be deleted outright.

## Building a new version

**Edit [`pins.yml`](pins.yml) and open a PR. That is the whole workflow.**

```yaml
provider: "0.11.0"     # was 0.10.0
bridge:   "1.3.0"
```

Or let the watcher notice for you. Either way the model is **propose, review,
merge** — CI never writes to `main`:

```
weekly cron ─▶ upstream newer than pins.yml? ── no ─▶ exit quietly
                       │ yes
                       ▼
       regenerate + run scripts/gate.sh INLINE
                       ▼
   open ONE PR: the pins bump AND the built SDK together
                       ▼
   human reviews and merges ─▶ CI passes on main ─▶ tag.yml cuts v0.11.0-sdk.1
```

The proposal carries `pins.yml` and the generated artifact **in a single
commit**, so the declaration and what was built can never disagree — which is
why the gate can enforce that they match exactly.

Tags chain off CI, not off the push: `tag.yml` runs only after the CI workflow
**succeeds on `main`**, so a merge that breaks the build in any way cannot
receive an immutable tag. If the watcher itself cannot reach the upstream
release listing, it **fails loudly** rather than reporting "nothing to do" —
an API outage and "you're up to date" must never look identical.

To bump on demand rather than waiting for the cron, run **Actions → Regenerate
SDK → Run workflow**. Blank inputs target the latest upstream release; fill them
in to pick specific versions. `force` rebuilds at the versions already declared
— and combined with an explicit `provider_version`, re-proposes a version whose
earlier proposal was closed (a closed proposal is treated as a human "no" that
the cron won't overrule on its own).

CI has **no write access to `main`** and holds no secrets. It pushes only its
own proposal branches.

The rest of this section is the summary. [`docs/pipeline.md`](docs/pipeline.md)
is the long form — the reasoning behind each of these choices, and a map of
which script does what.

### One gate, defined once

The definition of "the SDK is good" lives in [`scripts/gate.sh`](scripts/gate.sh):
install with zero lifecycle scripts, build, prove committed `bin/` is
reproducible **from nothing** (it is deleted before the build, which also
catches output of never-rebuilt new sources and stale output of deleted ones —
cases a plain `git diff` cannot see), assert `pins.yml` describes the built
artifact, and run the runtime + consumer smoke tests. `ci.yml` runs it on every
PR and push; the proposing workflow runs the same script before opening a PR —
so the two gates cannot drift apart.

### Why the gate runs before the PR exists

GitHub does not start workflows for events caused by the default
`GITHUB_TOKEN`, so `ci.yml` will not run on a PR this workflow opens. The gate
therefore runs *inside* the proposing job, which is the stronger position
anyway: a PR carrying a broken SDK is never created as a mergeable proposal.

So that the result is visible rather than buried in a log, the job stamps it on
the PR's head commit as the **`regenerate-gate` commit status** — the usual
green or red row in the merge box, linking to the run. Reporting a status is
allowed with `GITHUB_TOKEN`; only triggering workflows is not.

For an independent re-run on a fresh runner, **close and reopen the PR**: a
human reopening does trigger `ci.yml`.

### When the build fails

The proposal is still opened, deliberately. The likeliest failure is upstream
codegen drift that [`patch-sdk.sh`](scripts/patch-sdk.sh) refuses to guess at,
and a visible PR carrying its own reproduction beats a red cron run in an inbox
nobody reads.

Such a PR is marked four ways, and **each one independently prevents a
release**:

| Marker | Effect |
|---|---|
| Opened as a **draft** | Cannot be merged without a deliberate "ready for review" |
| `regenerate-gate` status **failing** | Red row in the merge box |
| **`build-failing`** label | Machine-readable state |
| **`BUILD-FAILURE.md`** committed to the branch | `tag.yml` refuses to tag any commit containing it, and `ci.yml` fails while it is present |

`BUILD-FAILURE.md` is committed rather than only written into the PR body
because Actions logs expire and a blocked proposal may sit for months. It
records the failing stage, the versions attempted, the captured gate output, and
how to resolve it.

To fix one: push to the branch — `ci.yml` **does** run on a human push and
reports the real result — then delete `BUILD-FAILURE.md`, drop the label, and
mark the PR ready.

### Why a declared pins file

`pins.yml` is **desired state**; `package.json` is **actual state**, written by
codegen. Keeping them apart matters — otherwise the input to regeneration is the
very artifact regeneration overwrites.

- Never hand-edit versions in `package.json`. Change `pins.yml`.
- `repackage.sh` asserts the built package matches the pins it was given.
- The two are only ever committed together, in one commit, so they cannot be
  observed disagreeing on any branch — which is exactly what lets the gate treat
  a mismatch as a hard failure rather than a transient state to tolerate.

Older tags remain consumable forever, so different downstream repos can sit on
different provider versions without this repository holding more than one.

### Keeping the watcher alive

GitHub disables scheduled workflows in public repositories after **60 days
without a commit**. Upstream ships roughly yearly, so expect the cron to lapse
between releases — re-enable it from the Actions tab, and treat the manual
dispatch as the path you can always rely on.

### Regenerating locally

```bash
scripts/regenerate.sh 0.10.0 1.3.0   # <provider-version> <bridge-version>
npm install && npm run build
git status                            # review the diff
```

Requires the `pulumi` CLI plus egress to `get.pulumi.com` and
`registry.opentofu.org`.

### What the regeneration scripts do

| Script | Responsibility |
|---|---|
| [`scripts/read-pins.sh`](scripts/read-pins.sh) | Read and validate `pins.yml`. Fails loudly rather than yielding an empty pin. |
| [`scripts/regenerate.sh`](scripts/regenerate.sh) | Pin the bridge plugin, run codegen, sync the generated surface into the repo, then call the two below. |
| [`scripts/patch-sdk.sh`](scripts/patch-sdk.sh) | Work around the upstream codegen bug. **Delete this file entirely once upstream is fixed.** |
| [`scripts/repackage.sh`](scripts/repackage.sh) | Re-apply this repo's deliberate packaging deviations (no lifecycle scripts, `bin/` committed, `NOTICE.md`), and assert the `pulumi.parameterization` block survived intact. |

They are separate on purpose: `patch-sdk.sh` is a temporary bug workaround with a
defined end of life, `repackage.sh` is permanent policy. Merging them would make
the workaround impossible to retire cleanly.

Those four are the chain you run by hand. The workflows call a further set —
deciding what to build, gating it, opening the proposal, cutting the tag — which
[`docs/pipeline.md`](docs/pipeline.md) inventories and explains. The workflow
files themselves only wire steps together; every non-trivial line of shell lives
in `scripts/`, where it can be read, linted and run outside CI.
